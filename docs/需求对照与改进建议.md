### 1.2 D01 文末遗留问题
> "`1到底谁有资格申请调离`"

当前实现只允许**人事**发起调离（`employment:submit` 只授予 HR），普通员工和项目经理均无入口。也就是说 D01 的这个悬而未决的问题，代码里已经"默认回答"成了"只有人事可以申请"，但没有任何文档或流程证据支撑这个决定。**建议在需求侧明确**：本人申请 / 直属主管申请 / 人事统一发起，三者选一并写进需求，否则后续加审批流会返工。

## 2. P0：上线前必须修（缺陷 / 越权 / 安全）

### P0-1 登录失败锁定机制实际失效（事务回滚） ✅ 已修复（第 1 轮）
- 证据：`UserServiceImpl.java:93-105`，`login()` 标注 `@Transactional`，失败分支先 `updateById` 累加 `failed_login_count`，随后 `throw BusinessException.unauthorized(...)`。`BusinessException` 继承 `RuntimeException`（`BusinessException.java:7`）→ 触发器默认回滚 → **计数与 LOCKED 状态永远不会落库**。
- 影响：README「连续 5 次密码错误将账号置为 LOCKED」与设计文档 5.1 的"简单限流/锁定"均为**不实描述**；口令可无限次爆破。
- 建议：失败计数改用独立事务（`REQUIRES_NEW`）或改为"返回错误码而非抛异常"；同时补"锁定自动解锁时长"与管理员解锁入口；补一个真实 DB 的集成测试证明计数值会增长。

### P0-2 没有"修改密码 / 重置密码"能力 ✅ 已修复（第 2 轮）
- 证据：全仓 grep `password|changePassword|resetPassword`，只有"创建用户时设初始密码"（`UserAdminController.java:91`），无改密接口、无重置接口、前端无入口。
- 影响：员工忘记密码只能改数据库；初始密码永久沿用；离职复用账号无法轮换口令；这在任何等保/审计口径下都是硬伤。
- 建议：`PUT /api/v1/profile/password`（验旧密码）+ `POST /api/v1/users/{id}/reset-password`（管理员重置，返回一次性初始密码或强制首登改密）+ `must_change_password` 字段。

### P0-3 项目详情 / 项目成员接口没有数据范围校验（越权）✅ 已修复（第 3 轮）
- 证据：`ProjectServiceImpl.java:85` `detail()` 与 `:122` `members()` 直接 `toVO(requireTeam(id))`，没有任何 `DataScopeService` 判断；Controller 只有 `@PreAuthorize('project:read')`（`ProjectController.java:49-51,70-72`）。
- 影响：**任何**持有 `project:read` 的账号（含普通员工，种子权限里就有）都能遍历 `/api/v1/projects/{1..N}` 与 `/{id}/members`，拿到全公司项目清单与成员姓名/工号/部门。这直接违反你们自己在设计文档 11. 验收标准里的「项目经理只能查看授权项目组及成员」。
- 建议：抽一个 `assertCanViewProject(current, team)`：`ALL/DEPARTMENT` 放行，`PROJECT` 要求"本人是负责人或有效成员"，`SELF` 只能看自己参与的项目。

### P0-4 部门员工列表绕过员工数据范围 ✅ 已修复（第 3 轮）
- 证据：`DepartmentServiceImpl.java:127` `employees()` 只按 `department_id` 过滤，无数据范围、无敏感字段控制。
- 影响：项目经理（`DEPARTMENT` 之外、`PROJECT` 范围）可以通过 `/api/v1/departments/{id}/employees` 拉取任意部门的员工姓名 + 工号 + 岗位 + 状态，绕过员工列表的范围过滤。
- 建议：查询前缀 `visibleEmployeeIds()`，或在 Controller 层复用 `EmployeeService.page` 并传 `departmentId`。

### P0-5 离职不联动：账号、项目成员、部门负责人全部悬空 ✅ 已修复（第 4 轮）
- 证据：`EmploymentServiceImpl.applyApproval()` 的 `RESIGN` 分支（`:284-286`）只改 `employment_status` 与 `resignation_date`；`SysUser` 状态不动（`UserServiceImpl.loadLoginUser` 只看 `sys_user.status`）；`project_team_member.left_at` 不动；`org_department.manager_employee_id` 不清空。
- 影响：离职员工凭旧 token/账号仍可登录（token 2 小时有效，账号永久可登），可继续看本人绩效、个人档案；`PROJECT` 范围仍把离职者算作"有效成员"；部门负责人指向离职员工后，审批/展示出现"幽灵负责人"。
- 建议：批准离职的同一事务内：`sys_user.status = DISABLED`、`project_team_member.left_at = effective_date`、提示/清空部门负责人、撤销未完成的绩效草稿；并补集成测试。

### P0-6 员工"编辑档案"可直改部门与岗位，绕开调岗流程 ✅ 已修复（第 5 轮）
- 证据：`EmployeeServiceImpl.java:122`（创建）与 `:173`（更新）直接 `setDepartmentId(request.getDepartmentId())`，`positionName` 同样可改。
- 影响：README 设计假设 7 声称"在职状态只能通过流程变更"，但**部门/岗位这两项最有业务含义的字段没有受控**，人事一次普通编辑就能完成一次"调岗"，且不产生任职历史，审计不可追溯。
- 建议：通用编辑接口禁止改 `departmentId/positionName`（或设为"仅当无在途调岗申请时可改，并自动补一条 TRANSFER 记录"），把变更统一收敛到流程。
- 已完成（第 5 轮）：`EmployeeServiceImpl.update()` 仅在员工处于 `PENDING`（待入职）时允许修正部门/岗位，其余状态改动直接 422 并提示提交 TRANSFER 申请；前端员工编辑弹窗对已入职员工禁用这两个控件并给出提示，避免用户填完才被拒。

### P0-7 生效日期被忽略，入转调离"即时生效" ✅ 已修复（第 5 轮）
- 证据：`EmploymentServiceImpl.process()`（`:130` 起，批准分支 `:261-291`）在批准瞬间改主档，完全不比较 `effectiveDate`。
- 影响：9 月 25 日批准"10 月 8 日入职"的员工，9 月 25 日就变成试用期；未来生效的离职提前进入离职态；薪资/考勤口径直接错。
- 建议：二选一——(a) 批准即生效，但 `effectiveDate` 强制 ≤ 今天（最简单的口径收敛）；(b) 保留未来日期，增加每日定时任务在生效日应用变更（`status=EFFECTIVE_PENDING` 中间态）。当前"填了日期但不用"是最差的一种。
- 已完成（第 5 轮）：采用方案 (a)。批准时若 `effectiveDate` 晚于今天直接 422 并提示"请在当天或之后办理；如需变更请驳回归还申请人修改"；驳回不受日期限制；前端办理弹窗对未到期申请禁用"确定"并展示原因。定时生效（方案 b）保留在 P2 待办。

### P0-8 无审批人概念，可自建自批 ◐ 部分修复（第 5 轮）
- 证据：`EmploymentServiceImpl.create()` 记录 `submittedBy`，`process()` 直接取当前用户为 `processedBy`，无任何 `submittedBy != processedBy` 校验；HR 角色同时拥有 `employment:submit` 与 `employment:process`。
- 影响：四眼原则缺失，审计上无法证明变更经过独立复核；设计文档虽允许"人事直接办理"的简化流程，但至少应阻止同一人自批，或引入"经办 + 复核"两个权限点。
- 建议：最小改动——`process` 校验 `!req.submittedBy.equals(currentUserId)`；进阶——加 `reviewer_user_id`、`approved_by` 两段式。
- 已完成（第 5 轮，部分）：`process()` 拒绝办理"涉及本人"的申请（`req.employeeId == 当前账号 employeeId`）并返回 403，杜绝人事给自己办转正/离职。未采用 `submittedBy != processor`：本系统只有一名 HR 同时持有 `employment:submit` 与 `employment:process`，强行拦截会让唯一人事无法办理任何申请。完整四眼（`reviewer_user_id` + 独立复核权限点，或 ADMIN 复核）仍在待办。

### P0-9 审计日志缺 IP、缺登录事件、缺变更前后值 ✅ 已修复（第 1 轮 IP + 登录三态，第 8 轮字段级 diff）
- 证据：`AuditService.record()`（`AuditService.java:22-40`）从不设置 `ipAddress`，而表里明确有该列（`schema.sql` `sys_audit_log.ip_address`）；登录、登出、登录失败均未写审计；`summary` 只写"更新员工档案 E0001"，无字段级新旧值。

- 已完成（第 8 轮）：新增 `common/audit/support/AuditDiff.java`，在写库前对实体取字段快照，写库后比对生成 "字段 旧值→新值" 文本；员工档案编辑（`EmployeeServiceImpl.update`）与入转调离批准（`EmploymentServiceImpl.process`）已接入，部门/直属主管自动换成名称，手机号、邮箱、住址、紧急联系人按掩码记录（如 `138****1111`），单条 diff 超长时截断并标注总项数。仍写 `summary`（TEXT）而非 JSONB，避免为加两列引入无 Flyway 的库结构迁移；后续如要按字段检索再演进为 JSONB。

## 3. P1：影响可维护性与业务正确性

### 3.1 权限模型
1. **数据权限粒度不足** — ✅ 已修复（第 21 轮）：新增 `sys_role_module_scope(role_id, module_code, scope_type)`，模块（`DataModule`：`EMPLOYEE/DEPARTMENT/PROJECT/PERFORMANCE/EMPLOYMENT`）级配置覆盖角色默认 `data_scope`；登录装配时按模块取多角色中范围最大者（`UserServiceImpl.moduleScopesOf`），`DataScopeService.effectiveScope/visibleEmployeeIds(user, module)/canAccessProject(user, team, module)` 统一按"模块优先、缺省回落角色级"解析，员工/部门/项目/绩效/入转调离/首页统计六处调用点都改为传模块。角色管理新增 `PUT /api/v1/roles/{id}/module-scopes`（`role:manage`，未知模块或非法取值 400，ADMIN 必须全为 `ALL`），前端角色编辑弹窗多了 5 个模块下拉（留空=沿用默认）。多角色合并仍是"取最大"而非并集/交集。原问题描述如下：`sys_role.data_scope` 是角色级单一枚举（`ALL/DEPARTMENT/PROJECT/SELF`），无法表达"人事可看全公司档案但绩效只看本部门""财务角色只能看指定 3 个部门"。设计文档 4.2 自己给了更好的方案（`sys_role_module_scope(role_id, module_code, scope_type)` 或 `sys_role_dept` 自定义部门集），实现时退化了。多角色合并取"范围最大"（`UserServiceImpl.scopeRank`）也是粗粒度近似，既不是并集也不是交集。
2. **数据范围枚举非法值会 500** — ✅ 已修复（第 13 轮）：`DataScopeService` 的取值统一走新私有方法 `parseScope()`（`trim().toUpperCase(Locale.ROOT)` 后 `valueOf`，失败按最小权限降级为 `SELF` 并 `log.warn`），列表过滤与 `canAccessProject` 两条路径都改用它，脏数据不再冒 500。

21. **JWT 不可撤销** — ◐ 部分修复（第 17 轮）：新增 `sys_user.token_version` 与 JWT 的 `ver` 声明（`JwtAuthenticationFilter.sameTokenVersion`），本人改密与管理员重置密码都会 `bumpTokenVersion`，旧 token 立即失效（`JwtAuthenticationFilterTest` 5 例覆盖，含升级前无 `ver` 声明的兼容）。**仍存**：角色/权限调整不提升版本，会话本身到过期才失效（权限每请求重查，实际权限已即时收窄）；「只踢会话不停号」无入口；无 refresh token，2 小时到期需重新登录；token 仍存 `localStorage`，XSS 可窃取，更严做法是 httpOnly Cookie + CSRF。
22. **审计写入与业务同事务且异常吞掉**：`AuditService.record` catch 后仅 warn（若同连接已进入 aborted 状态，后续 commit 会连带失败），审计可靠性未定义。

## 4. P2：性能与工程质量

### 4.1 后端
1. **N+1 查询普遍** — ✅ 已修复（第 25/27 轮）：原来 `PerformanceServiceImpl.toVO` 每行 5 次查询（员工、评价人、项目组）、`ProjectServiceImpl.toVO` 每行一次 `count(*) member`、`EmploymentServiceImpl.toVO` 每行查员工 + 2 次查用户名、`UserAdminController.toVO` 每行查角色。第 25 轮改为列表接口先收集本页 id，用 `selectBatchIds` 一次查回 Map 再组装（绩效列表、绩效申诉、项目组列表与成员、任职记录、用户列表）；第 27 轮把部门树与部门分页的负责人姓名也改为一次批量查回，防环校验改为一次取回全部 `id → parent_id` 在内存回溯（原本按层级逐次 `selectById`）。单条详情仍走单行查询，属于合理范围。
2. **数据范围计算成本随规模放大**：`expandDepartmentIds` 每次 `selectList(null)` 拉全部部门在内存建树；`departmentVisibleEmployeeIds` 再把整个部门的员工 ID 全部塞进 `IN (...)`。200 人无感，一旦部门/人数上千，列表页会明显变慢。建议改 SQL 递归 CTE（`WITH RECURSIVE`）+ `EXISTS`。
3. **每请求 5 次查询装配权限**（user/roles/permissions/employee/roles-permissions）且无缓存；200 人可接受，但应写清扩展路径（本地 Caffeine 5 分钟 + 权限变更主动失效，仍不违反"不引入 Redis"）。
4. **无乐观锁**：`employee`、`employee_change_request`、`performance_review` 均无 `version` 字段；两个 HR 同时点"批准"会产生两条任职历史（状态判断是 read-then-write）。
5. **无迁移工具**：`schema.sql` 手工执行，无 Flyway/Liquibase，无版本号、无回滚脚本。生产第一次加字段就会开始"人肉 alter"。设计文档 13.10 明确允许 Flyway，建议尽早引入。
6. **无 Actuator/健康检查指标**：只有 `/api/v1/health` 返回常量，无 DB 连通性、无 JVM/连接池指标、无 traceId，出问题只能看日志。
7. **异常映射不全** — ✅ 已修复（第 16 轮）：`GlobalExceptionHandler` 增加 `DuplicateKeyException` → 409 `DUPLICATE_KEY`、`DataIntegrityViolationException` → 400 `DATA_INTEGRITY_VIOLATION`（提示必填缺失/关联不存在/内容超长），SQL 细节只进 WARN 日志；`GlobalExceptionHandlerTest` 3 例覆盖。

## 7. 做得好的地方（不要改坏）

- 技术栈严格贴合 D02，没有为了"看起来高级"引入 Redis/MQ，符合"最小技术栈"约束。
- 分层清晰（controller/dto/service/entity/mapper/vo），命名一致，`ApiResponse`/`PageResponse` 统一，`GlobalExceptionHandler` 分类合理。
- 权限校验在服务端 `@PreAuthorize` + 数据范围二次过滤，前端隐藏只是体验层——方向正确。
- `DataScopeService` 把"可见员工集合"收敛成单一出口，思路好（只是粒度与性能需补）。
- 部门防环校验、分页上限 100、`BlockAttackInnerInterceptor` 防全表更新、JWT 密钥长度启动自检，都是有意识的质量措施。
- 敏感字段按"是否本人/是否全量范围"控制，返回 VO 而非实体，避免密码哈希外泄。
- README、`implementation-design.md` 的自查口径诚实（明确写了"纯 JWT 无法服务端撤销"），这点比大多数项目强。
